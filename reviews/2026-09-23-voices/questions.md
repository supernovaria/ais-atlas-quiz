**What changed, and why.** Two additions to the blind-reader layer. (1) A panel of non-Claude readers (Gemini, Gemma, Mistral, and free OpenRouter models such as GLM, Qwen and Nemotron), called by `scripts/voices.mjs`, which answer the same prompt files the Claude adversary answers. The reason: readers that share pretraining share priors, so a leak one Claude model finds in another Claude model's questions may be a family artifact rather than something any reader would exploit. (2) An **explain** mode (`prompts/adversary-explain.md`): per option, a probability and cue codes from a fixed list (`prompts/_partials/tell-codes.md`), with `other` plus a free-text note and `no-tell`. `pipeline.mjs ablate-score` aggregates these into `tells.json`/`tells.md`: how often each code sits on keys vs distractors ("lift"), and whether claimed cues match what the checker can measure in the text (e.g. `most-detailed` vs actually longest; `echoes-stem` claimed on a rung where no stem was shown). The explain mode is diagnosis only; the letter-only rungs stay the score. The intended use of the result: find recurring tells in the generator's output and turn them into generator-brief changes and mechanical checks.

**Specific questions.** Answer these in addition to anything else you find.

1. **The code list.** Is `tell-codes.md` missing a cue a test-wise reader really uses on multiple-choice questions? Are any two codes so close that readers will use them interchangeably, which would split one real signal into two weak ones? Does the grouping into "look right / look wrong / either way" push readers to attach codes in a particular direction, and is that a problem for the lift analysis?

2. **Does explaining change what is measured?** Readers in explain mode assign probabilities and codes before picking. Is keeping those hit rates apart from the letter-only rungs enough, or does the explain mode also bias the *codes*, e.g. readers rationalising after an intuitive pick, and so naming the most nameable cue rather than the real one? What in the design would detect that? The faithfulness table and the impossible-claim count are the current attempt.

3. **Lift as the headline statistic.** Lift is rate-on-keys / rate-on-distractors, pooled over voices and questions. Where does that mislead? Consider one voice dominating the count, one question contributing most tags, and codes that are correlated (`most-detailed` and `nuanced-turn` often co-occur). Is there a better simple statistic for "this cue identifies the key"?

4. **Pooling voices.** The letter-only panel pools every voice's trials per question, with the question as the unit of the interval. The voices differ widely in strength (8B to frontier). Is a pooled panel hit rate meaningful, or should the headline be per voice, or per family? What should the pre-registered prediction be stated against?

5. **The queue.** `voices.mjs` treats 503s and upstream 429s as "retry later" (nothing written), daily caps and auth failures as "voice down until reset", and a rejected optional setting (thinking level, JSON mode) as "drop it and retry", recording the drop. Can any of these make two runs of the same manifest differ in a way the scoring would not show? Is any failure silently counted as an answer, or an answer silently lost?

6. **Parity across voices.** Every voice gets the byte-identical prompt file. Only API settings differ: lower thinking for letter mode on Gemini, JSON mode for explain mode where supported. Does either difference undermine the comparison between voices, or between API voices and the Claude subagent, which gets neither?

7. **Feeding it back.** The plan is to give the critic the aggregated cue codes as evidence for its believability judgment, and to give the generator only the cues (not the winning letters) in a rewrite pass for flagged questions. One voice family is held out of the feedback and used only to measure. Where does this still Goodhart? What would you hold out, and how much?

8. **Parsing.** `parseExplainReply` in `pipeline.mjs` claims to parse and never repair: it unwraps one code fence, drops unknown codes (recording them), and marks a reply unusable if it lacks an entry for every shown letter. Any way a malformed reply is counted as usable when it should not be, or the other way round?
